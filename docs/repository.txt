app/repository.js
=================

createRepository(db, table, config)
-----------------------------------

A plain, schema-agnostic CRUD helper that lives in app/ — not in
lib/. It is a convenience wrapper around a raw database handle for
building SQL repositories by hand, outside the schema-aware path.

When to use this vs schema.repository()
---------------------------------------

    schema.repository(adapter, 'User')
        Schema-aware. Knows field types, converts booleans/datetimes/
        json to/from storage automatically, derives the table name.
        This is the default for app code. (docs/persistence.txt,
        docs/schema.txt)

    createRepository(db, 'users', { primaryKey: 'id' })
        Schema-agnostic, SQL-flavored. No conversions, no naming
        magic. Useful for hand-written SQL layers, legacy tables,
        or ad-hoc micro-repositories that don't map to an entity.

Signature
---------

    createRepository(db, table, config = {}) -> repository

    db      a raw database handle (adapter.database):
            { query, execute, get, transaction, close }

    table   the exact storage name, e.g. 'users'

    config  { primaryKey = 'id' }   // identity column name

Methods
-------

    findAll({ orderBy = 'id DESC', limit, offset } = {})
    findById(id)                    -> row | null
    findBy(criteria)                -> rows   // { col: value, ... }
    create(data)                    -> row
    update(id, changes)             -> row | null
    delete(id)
    count(criteria = {})            -> number

Important behaviors
-------------------

  - NO auto-timestamps. What you write is what is stored. If you
    want created_at, pass it explicitly or build a richer
    repository (see below).
  - The caller owns the storage name. There is no pluralization,
    no mapping — table is written into the SQL as-is.
  - Row results are RAW storage values (strings, ints, ISO datetimes
    as plain text). No fromDB conversion. Render quickly, understand.
  - This is an SQL convenience. It lives in app/ because it is a
    SQLite-specific pattern, not a framework primitive.

App-level usage
---------------

App repositories use createRepository as a base and layer
application conventions on top:

    const { createRepository } = require('../repository');

    const createUserRepository = (db) => {
        const repo = createRepository(db, 'users', { primaryKey: 'id' });

        return {
            ...repo,

            create: (data) => {
                const now = new Date().toISOString();
                return repo.create({
                    ...data,
                    created_at: data.created_at || now,
                    updated_at: data.updated_at || now
                });
            },

            update: (id, changes) => {
                const now = new Date().toISOString();
                return repo.update(id, {
                    ...changes,
                    updated_at: changes.updated_at || now
                });
            },

            findByEmail: (email) =>
                repo.findBy({ email }).then(users => users[0] || null)
        };
    };

Conventions stay in YOUR code; the framework never needs to know
about soft delete, slugs, or timestamps.

Extending a schema.repository
------------------------------

Repositories are plain objects (both styles). Extend them wherever
you build them — no subclassing, no framework hooks needed:

    const usersRepo = schema.repository(adapter, 'User');

    usersRepo.softDelete = (id) =>
        usersRepo.update(id, { deleted_at: new Date() });

    usersRepo.findBySlug = (slug) =>
        usersRepo.findBy({ slug }).then(rows => rows[0] || null);

Conventions stay in YOUR code; the framework never needs to know
about soft delete or slugs.

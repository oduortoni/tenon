lib/repository.js
=================

createRepository(db, table, config)
-----------------------------------

A plain, schema-agnostic CRUD helper. You bring the storage name
and the primary key; it gives you a small repository object that
talks to that ONE table.

Signature
---------

    createRepository(db, table, config = {}) -> repository

    db      a framework-shaped database object:
            { query, execute, get, transaction, close }
            (docs/database.txt, docs/persistence.txt)

    table   the exact storage name, e.g. 'users'

    config  { primaryKey = 'id' }   // identity column name

Methods
-------

    findAll({ orderBy = 'id DESC', limit, offset } = {})
    findById(id)                    -> row | null
    findBy(criteria)                -> rows   // { col: value, ... }
    create(data)                    -> row
    update(id, changes)             -> row | null
    delete(id)
    count(criteria = {})            -> number

Important behaviors
-------------------

  - NO auto-timestamps. What you write is what is stored. If you
    want created_at, pass it explicitly or build a richer
    repository (see below).
  - The caller owns the storage name. There is no pluralization,
    no mapping — table is written into the SQL as-is.
  - Row results are RAW storage values (strings ints, ISO datetimes
    as plain text). No fromDB conversion. render quickly, understand.

When to use which repository
----------------------------

Two repository styles exist:

  schema.repository(adapter, 'User')
      Schema-aware. Knows field types, converts booleans/datetimes/
      json to/from storage automatically, derives the table name.
      This is the default for app code. (docs/schema.txt,
      docs/persistence.txt)

  createRepository(db, 'users', { primaryKey: 'id' })
      Schema-agnostic. No conversions, no naming magic. Useful for
      hand-written SQL layers, legacy tables, or micro-adapters.

Appending application conventions
---------------------------------

Repositories are plain objects (both styles). Extend them wherever
you build them:

    const usersRepo = schema.repository(adapter, 'User');

    usersRepo.softDelete = (id) =>
        usersRepo.update(id, { deleted_at: new Date() });

    usersRepo.findBySlug = (slug) =>
        usersRepo.findBy({ slug }).then(rows => rows[0] || null);

Conventions stay in YOUR code; the framework never needs to know
about soft delete or slugs.
